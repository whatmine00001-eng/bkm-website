## 4. Формы, лиды и персональные данные
- Целевая цепочка: браузер 24bkm.com -> POST /api/lead.php на Beget -> приватный REST-вебхук -> коробочный Bitrix24 (`https://bitrix.24bkm.com`), объект именно **лид**, а не сделка; назначать на Кирилла (`ASSIGNED_BY_ID=7`).
- 28.10.2026 подтверждён реальный безопасный CLI-тест Beget -> Bitrix24: служебный лид ID 6 создан и прочитан, ответственный 7; это НЕ тест публичной формы. См. `BITRIX_WRITE_TEST_2026-10-28.md`.
- 30.10 на сайте была опубликована только локальная тестовая форма: кнопка «Проверить заполнение», тестовые подсказки, без отправки клиентских данных и без создания лида; `FORM_NETWORK_STATUS_2026-10-30.md`. Пользователь требует удалить тестовые элементы и активировать настоящую форму.
- Исходный `assets/site-config.js` по умолчанию содержит `formsEnabled: false, analyticsEnabled: false`. Реальная CRM-сборка переводит публичный флаг в true только внутри сборки `BKM_CRM_RELEASE=on`; не изменять исходный флаг вручную.
- Утверждённые владельцем HTML-политика и отдельное согласие находятся в `approved/privacy.html`, `approved/consent.html`; они прошли CI build-only dry run 30.10, run 41071004346. Политика подготовлена для выпуска, но факт её наличия в public_html и юридические организационные действия необходимо проверить.
- Приватная конфигурация Beget за пределами web root: `/home/h/help24pw/.bkm_private/config.php`. Ранее `enabled=false`, `privacy_approved=false`. **Нельзя** утверждать, что флаги включены сейчас, без чтения состояния сервером. Никогда не помещать приватный вебхук или секреты в GitHub, логи или переписку.
- `api/lead.php` проверяет HTTPS/Origin/Host, поля, согласие, rate limit, серверный вебхук, возвращает успех только после подтверждения созданного ID. Избегать автоматических повторов при сетевой неопределённости.
- Сценарий ручного выпуска: `main` -> Actions -> `prepare-beget-production.yml`, сначала `mode=prepare`, `crm_mode=on`, потом только после server preflight `mode=publish`, `crm_mode=on`, `confirmation=RELEASE_24BKM`. Выпуск делает резервную копию. Следует обязательно проверить, какой commit ветки дизайна берётся workflow, прежде чем применять релиз.
- При активации: проверить физическое наличие privacy/consent, конфигурацию и методы Bitrix24, затем один контролируемый end-to-end тест через опубликованную форму с согласия владельца; отдельно проверить назначение и уведомления.

## 6. Разработка / SEO / маркетинг после формы
- Приоритет владельца: (1) сохранить смелый тёмный дизайн; (2) убрать тестовые элементы и повторы; (3) включить настоящую форму и проверить поступление лидов; (4) SEO/Яндекс Метрика/контент.
- Улучшить SEO: чистые title/description/canonical, sitemap/robots, 301 на одну HTTPS-версию, internal linking, структурированные данные Organization/Service при подтверждённых данных, скорость, локализация удалённых шрифтов/Unsplash-изображений, доступность, качественные страницы направлений; результаты не гарантируют «всегда топ».

Опора на официальные первоисточники, проверять даты и юридическую точность; контент должен продавать услуги БКМ и приводить к обращению.

## 7. Нерешённые организационные вопросы
- Владелец ранее передал утверждённую политику, но проверка организационных обязанностей оператора данных (в том числе применимость уведомления Роскомнадзору, сроки хранения, отзыв согласия, доступ, логи/резервные копии) должна быть выполнена отдельно и не заменяется техническим маркером.

- Следующая техническая операция — убедиться, что browser CI прошёл и подготовить/проверить **ручной CRM-релиз** в приватной staging-папке; производство менять только после preflight и резервного копирования. Не принимать решения по старым заметкам без актуальной проверки.
